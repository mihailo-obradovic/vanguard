# Frontend Addon: Internationalization

**Category:** i18n
**Tool:** @nuxtjs/i18n

Adopt when the product is user-facing in more than one language, or in a single language that isn't English. A single-language English product does not need it.

- `@nuxtjs/i18n` (v10, over Vue I18n 9+): `$t` / `useI18n()` in components, `setLocale()` to switch, `useNuxtApp().$i18n` where a composable can't run.
- Message catalogs are the **single source of truth** for user-facing text — they live under the module's `restructureDir` (default `<rootDir>/i18n`), catalogs in `i18n/locales/`. A project whose Nuxt app sits under a non-default `srcDir` sets `restructureDir` to keep them with the frontend (`srcDir: 'web/'` → `restructureDir: 'web/i18n'`) — the default resolves from the **root** directory, not `srcDir`.
- Catalog files are named by the locale code as the routing config spells it, in BCP 47 form (`sr-Latn.json`, never `sr_Latn.json`).
- **One file per locale** while the catalog is small (roughly under ~300 keys), with the namespaces as top-level keys inside it — `locales[].file`. Split into per-namespace files (`locales[].files`, a `<locale>/` directory each) only once a single file stops being reviewable; every file must then be hand-registered in the config, which is the cost that buys the split.
- On the client-rendered baseline (`../nuxt.md` — the app is an SPA) there is no server to negotiate a locale or serve prefixed routes for crawlers, so the default is **`strategy: 'no_prefix'`** with `detectBrowserLanguage` persisting to a cookie: no locale in the URL, no `localePath()` wrapping on every link, and nothing for the auth middleware to fight with. The `ssr` addon is what makes a prefix strategy worth its cost — adopting SSR is when locale-prefixed routes, `useLocaleHead`, and hreflang become live options.
- Vue I18n build-time configuration lives in `<restructureDir>/i18n.config.ts` (resolved relative to `restructureDir`, not `nuxt.config.ts`): `fallbackLocale`, `datetimeFormats`, `numberFormats`, and `pluralRules` for any locale whose plural system Vue I18n's index-based default doesn't fit.
- Locale-aware formatting goes through the active locale, never a hardcoded tag — a `formatDate`-style helper takes the locale from `useI18n()` rather than pinning `'en-US'`.
- At adoption, the project records its locale set in `project-summary.md` (the Technical Stack row for this addon); the documents here keep the set parameterized as `<locales>`.

The addon ships a payload directory `i18n/` holding the catalog hygiene rules ([`i18n/catalog-hygiene.md`](i18n/catalog-hygiene.md)) and the audit procedure ([`i18n/audit-i18n.md`](i18n/audit-i18n.md)), copied into a project only when the addon is chosen.

## UI-Library Strings

A component library ships its own internal strings (data tables, pagination, date pickers) that the catalogs do not cover. Where the `frontend/ui` choice supports a Vue I18n adapter, wire it so one locale switch moves everything: Vuetify exposes `createVueI18nAdapter` from `vuetify/locale/adapters/vue-i18n`, fed `$vuetify` message trees built from its own bundled locales, and requires `legacy: false` — which is the module's default. A headless UI choice has no such surface and needs nothing.

## Editor

The addon brings the `lokalise.i18n-ally` recommendation with it, but Catalyst writes no `settings.json` ([`conventions/editor-setup.md`](../../../../conventions/editor-setup.md)) — without these keys the extension finds no catalogs and shows nothing. Paste into the project's `.vscode/settings.json`, with `<langDir>` replaced by the repo-relative catalog directory:

```json
{
  "i18n-ally.localesPaths": ["<langDir>"],
  "i18n-ally.keystyle": "nested",
  "i18n-ally.dirStructure": "file",
  "i18n-ally.sourceLanguage": "<primary locale>",
  "i18n-ally.enabledFrameworks": ["vue"]
}
```

`sourceLanguage` is the locale the catalogs are authored in, spelled as a BCP 47 tag (`sr-Latn`, never `sr_Latn`) — the extension normalizes catalog filenames to that form and matches this value against the result. `keystyle` is `nested` because the catalogs are namespaced ([`i18n/catalog-hygiene.md`](i18n/catalog-hygiene.md), Placement). `dirStructure` is `file` for one-file-per-locale; a per-namespace split instead needs `"i18n-ally.pathMatcher": "{locale}/{namespace}.json"` with `"i18n-ally.namespace": false`.

**Hard rule:** every user-facing string goes through the catalog **from day one**.
