# Operations Runbook

Per `references/operations-runbook.md`: one section per stateful component — **Operate** / **Recovery** / **Quirks**. Commands and traps only; rules live in `architecture.md` and the feature docs.

## MySQL

Host-local server (no Docker/Sail), database `vanguard` at `127.0.0.1:3306`, credentials in `.env`. Holds application tables plus sessions, cache, and the (currently idle) jobs queue.

### Operate

```bash
php artisan db:show                # connection + table overview
php artisan migrate:status         # which migrations have run
php artisan tinker                 # poke at data
mysql -u <DB_USERNAME> -p vanguard # interactive client
```

One-time test-database provisioning (as MySQL root; `RefreshDatabase` migrates it on each run):

```bash
sudo mariadb -e "CREATE DATABASE IF NOT EXISTS vanguard_testing; GRANT ALL PRIVILEGES ON vanguard_testing.* TO '<DB_USERNAME>'@'localhost'; FLUSH PRIVILEGES;"
```

### Recovery

No backup routine exists — dev-only data so far; a restore drill has never been performed. Recreate from scratch with `php artisan migrate:fresh --seed` (seeder creates `test@example.com` admin). **Before any production use, a dump/restore routine must be added here and rehearsed.**

### Quirks

- Tests run on the separate `vanguard_testing` database on this same server (same engine, per the Laravel testing module): `phpunit.xml` pins `DB_CONNECTION`/`DB_DATABASE`; host and credentials are inherited from `.env` (no `.env.testing` exists — creating one would silently take over the test env, since `APP_ENV=testing` prefers it). `php artisan test --parallel` would need databases `vanguard_testing_1..n` — not provisioned.
- Sessions live in the `sessions` table (`SESSION_DRIVER=database`): truncating it logs everyone out; deleting a user leaves orphaned session rows (no FK).

## Queue

`QUEUE_CONNECTION=sync` in the local `.env` — queued notifications (verification + reset mail) execute inline in the request. The `jobs` table and the `queue:listen` process in `composer run dev` are ready for the `database` driver but idle under `sync`.

### Operate

```bash
php artisan queue:listen --tries=1   # only meaningful with QUEUE_CONNECTION=database
php artisan queue:failed             # inspect failures (database driver)
```

### Recovery

Under `sync` there is nothing to recover — a mail failure surfaces as a request error. Under `database`, failed jobs land in `failed_jobs`; retry with `php artisan queue:retry all`. Never drilled.

### Quirks

- Switching to `database` without running a worker silently strands all auth mail in the `jobs` table.

## Mail

Mailtrap sandbox SMTP (`sandbox.smtp.mailtrap.io:2525`, creds in `.env`) — all mail is captured, nothing reaches real inboxes.

### Operate

Check the Mailtrap inbox for verification/reset mails; `php artisan pail` (part of `composer run dev`) tails mail-send log entries.

### Quirks

- `MAIL_FROM_ADDRESS` is still `hello@example.com`.

## Dev stack

### Operate

```bash
composer run dev    # serve (localhost:8000) + queue:listen + pail + pnpm run dev
php artisan serve   # API alone
pnpm dev            # SPA alone (localhost:3000)
php artisan test && pnpm test   # both suites
composer test:coverage          # backend coverage (sets XDEBUG_MODE=coverage; needs the Xdebug extension)
composer test:coverage-html     # same, plus browsable report into reports/coverage-backend/ (gitignored), opened in the browser
pnpm test:coverage              # frontend coverage (text + html + lcov into coverage/, gitignored)
pnpm test:ui                    # Vitest browser dashboard, watch mode with coverage embedded
composer test:mutation          # backend mutation audit (below)
pnpm test:mutation              # frontend mutation audit (below; preflight-checked)
composer format                 # backend formatter (Pint, laravel preset); composer format:check to verify only
pnpm format                     # frontend formatter (oxfmt); pnpm format:check to verify only
```

Mutation audit (ADR 013; run after a test-writing push, not on a schedule): `composer test:mutation` mutates `app/` (Pest's built-in mutation testing; `--everything` because classes carry no `covers()` annotations, `--covered-only` to skip mutations no test executes) and reruns the covering tests per mutant. **Do not add `--parallel`** — mutant processes share the `vanguard_testing` database and would trample each other. Every listed _untested_ mutation is a change no test noticed — fix the test it exposes or record here why the mutant is acceptable. Score is a measurement, never a gate.

Current figures (re-measure before trusting: `composer test:coverage`, `composer test:mutation`): coverage **100% lines**; mutation **82.06%** (262 mutations, 47 surviving, all triaged below).

Accepted surviving mutants — recheck when touching the code they live in:

- **Events with no listeners** — removing `event(PasswordReset|Verified|Lockout)` is unobservable because nothing consumes them yet; the day a listener lands, its tests kill these.
- **Rule-list residue** (the largest group, ~15): `'sometimes'` on a field with no `required` beside it — Laravel skips non-implicit rules on an absent attribute anyway, so the mutant is behaviorally identical; `'string'` on a field whose format rule already rejects non-strings (`validateEmail` does); `'string'` on the GraphQL validator's `name`, unreachable because the schema types the argument `String`; and `'email'` on `LoginRequest`, where a malformed address fails the credential check into the same 422.
- **Password-broker message copy** (`PasswordResetLinkController` rules and both `!=` → `!==` on the status strings): every path already answers 422 keyed `email`; killing these would mean pinning broker message text, which is copy, not contract.
- **Throttle message copy and key residue** — `minutes` and its `ceil` are never rendered (no `lang/` is published and the framework's `auth.throttle` interpolates only `:seconds`); the `'|'` separator and the concat order leave the key unique per (email, IP) pair either way. The parts that _are_ contractual — the threshold of 5, the seconds in the message, the counter clearing on success, and scoping to both email and client address — are pinned now.
- **`remember_token` rotation** (`Str::random(60)` length and the array item on reset) — a deliberate hold: the `remember` flow is a recorded feature-doc gap, and pinning half of it here would document behavior the contract does not yet claim.
- **Session regeneration in the controllers** (`AuthenticatedSessionController::store`, `RegisteredUserController::store`) — `Auth::login()` already calls `$this->session->regenerate(true)`, so removing the explicit call changes nothing observable. Verified by hand, not assumed.
- **Defensive code unreachable through routes**: `UserRequest::authorize()`'s `&&` (route middleware guarantees a user), `ResourcePayload`'s JSON depth and assoc flags (Lighthouse's default resolver reads arrays and objects alike), `array_intersect_key` unwraps in both `UpdateUser`s (inputs are pre-filtered by both transports' validators).

Frontend mutation audit (ADR 013; `stryker.config.json`, same cadence and triage rule as the backend's). The mutate globs cover the logic layers — `web/utils`, `web/services`, `web/stores`, `web/composables` — plus `web/plugins`, `web/regle-config.ts`, `web/i18n/i18n.config.ts`, and the component surface: `web/components`, `web/layouts` and `web/app.vue`. Pages and middleware stay out — the presentation exception (`decisions/013`): every mutant there would report as noise rather than signal. Nothing is excluded by name. The untested composables stay in scope on purpose: Stryker separates `NoCoverage` from `Survived` and prints a covered-code score beside the total, which is the honest analogue of the backend's `--covered-only` without a hand-maintained exclusion list that rots.

Two things about `.vue` in particular:

- **Stryker mutates only the `<script>` block.** Template logic is never mutated, so a component whose branching lives in the template — `UsersTable`'s `v-if="deletable && user.id !== currentUserId"`, for instance — scores on its script alone and can read as 0% while being thoroughly tested. The same fact is why several components yield no mutants at all: `SkipLink` and `Empty.vue` have no script, `TheFooter` derives one constant, and master's `Default.vue` is three lines of composable calls. Master's `UIField` is the inverse case: the message it shows is a template expression (`errors?.[0] ?? ''`) and goes unmutated, while the aria wiring its script derives does not. Read a `.vue` score as a statement about its script, not about the component.
- **Compiler macros must be excluded from instrumentation where they are used.** Stryker declares its coverage helpers locally inside the script block, and `withDefaults(defineProps<…>(), { … })`, `defineModel(…, { … })` and `defineOptions({ … })` are hoisted out of `setup()` — referencing the helpers from there is a `@vue/compiler-sfc` compile error, not a warning. Every affected component therefore carries a `// Stryker disable all` / `// Stryker restore all` pair around its macro block; the prop defaults, model options and component options inside go unmutated as a result. Fourteen components need it on `variant/vuetify`; on `master` only `UIField` does, for the `defineOptions({ inheritAttrs: false })` its attribute fall-through needs; on `variant/nuxtui` seven do — the six dialogs' `defineModel('open', …)` and `UFormField`'s `defineOptions`. Do not drop those pairs when merging in either direction.

  **The failure is not always loud.** On `variant/vuetify` it fails the whole dry run with a message naming only the first file it hit. On `UIField` it did something worse: the compile error hit only the spec that imports the component, that one file silently contributed zero tests, and the run completed reporting **every mutant in the file as survived** — a 0% score that reads as "untested" rather than "not compiled". The tell is the test count in the dry run (267 of 276) and `Ran 267.00 tests per mutant`, where a working `.vue` run attributes a handful. A component whose own spec demonstrably fails when its logic is broken by hand, yet scores 0%, is this, not a weak test.

  `defineModel` fails silently in a third way: its instrumented arguments are hoisted into the module-scope `props:` object, so the component throws `ReferenceError: stryMutAct_9fa48 is not defined` at import time rather than failing to compile. On `variant/nuxtui` that made seven spec files (44 tests) — the six dialog specs and `Default.spec.ts`, whose import chain reaches the dialogs — collect zero tests each, and the dry run reported success on the shrunken set. The tell is the same: compare the dry run's test count against `pnpm test`'s before trusting any figure.

- **Per-test attribution is narrower than coverage.** Stryker runs only the tests it recorded as covering a mutant, and for a mutant inside an `if` condition that set can exclude the tests taking the _other_ branch. `UIDialog`'s focus-trap condition (`event.shiftKey && …`) is reported as survived for exactly that reason: its covering set is the two Shift+Tab specs, both of which pass under it. Forcing the branch by hand turns **four** specs red. Before writing a survivor off as a missing test, break it in the source and run the spec — the covering set in `reports/mutation/frontend.json` says which tests the score actually reflects.

Accepted surviving mutants on `master`'s components — recheck when touching the code they live in:

- **`UIDialog`'s panel null guards** (`panel.value?.querySelectorAll`, `panel.value?.focus()`, and the `?? []` beside the first, which is reported as uncovered) — the panel exists whenever the handlers can run: they are bound to it. Defensive, unobservable. The _opener_ guards are no longer on this list — `opener?.isConnected` and the `?.` on the `#main-content` lookup are both killed by the two dead-opener specs.
- **`UIDialog`'s `if (!first || !last) return`** (both the condition and `||` → `&&`) — with nothing focusable inside, `first` and `last` are both `undefined` and the two `active === …` comparisons below match nothing anyway, so the guard changes no outcome. It stays because it states the intent and stops the queries.
- **`UIDialog`'s Shift+Tab condition** — the attribution artifact above, verified by hand rather than assumed.
- **`UserGqlFormDialog`'s empty-form fallbacks** (`user?.name ?? ''` and its two siblings) — `user === null` is what closes that dialog, so those values only ever feed a form nobody can see; the visible ones come from the watcher's reseed.
- **`UserFormDialog`'s `props.user?.id`** — the getter only runs from the availability rule, which is `try`/`catch` fail-open by design (feature 008), so the `TypeError` the mutant causes in create mode is swallowed into "available" exactly like a network failure. Worth knowing: that catch masks programming errors as well as outages.
- **All three form dialogs' reset guards** (`if (!open) return`, and `UserGqlFormDialog`'s `if (!user) return`) — resetting on the way closed as well as open changes nothing: the content unmounts in between, so resetting on either edge leaves the same form on the next open. (In `ProfileFormDialog` even the inverted `if (open) return` survives, for the same reason.)
- **All three form dialogs' `clearExternalErrors: true`** — prescribed by `stacks/frontend/nuxt/validation.md` and kept for that reason, but unobservable here: `$reset` alone hides the verdict (Regle keeps errors off a pristine field), and editing the field clears the entry from the bridge's ref before any resubmit can surface it. Tested from the user's side instead — "does not bring the last attempt's verdict back on the next submit" — which is the behaviour, whichever line delivers it.

`pnpm test:mutation` runs `scripts/preflight-mutation.mjs` before Stryker. It exists because the two ways this run breaks both report something unrelated to the cause: a missing `.nuxt/tsconfig.app.json` surfaces as a bare "No tests were found", and a `node_modules/.modules.yaml` pointing into the sandbox surfaces as every later pnpm command demanding to purge `node_modules`. The preflight names each one and prints the fix. Both branches of it were proven by breaking the tree on purpose, not by reading the code.

One more trap, which no preflight can catch: **a crashed run still leaves the previous report in place**, and piping the command to something like `tail` hides the non-zero exit. The tell is a rerun that reproduces the previous score exactly — check `reports/mutation/frontend.json`'s modification time before believing it.

**Run it through `pnpm test:mutation`, never `npx stryker run` directly.** Bypassing the preflight to measure one file quickly — `npx stryker run --mutate <file>` — produced three different scores for the same committed code in one sitting (72%, 79%, then 24% reproduced three times, including against a clean checkout of the spec). Nothing in the source moved between them. The cause is most likely the cold-sandbox hook timeout resolved below — which spec files get skipped varies with how warm the transform cache happens to be — but a targeted raw run is still not a measurement you can quote, and the divergence is silent: every run reports a confident number. Break the source by hand and run the spec instead — that is the check this document already prescribes for a single survivor, and it is the one that held up every time.

Four config choices are load-bearing and easy to undo by accident:

- **`ignorePatterns` is only `!.nuxt`.** Stryker honors `.gitignore`, so nothing else needs listing — excluding the Laravel directories on top was measured and changed neither the score nor the wall clock (488K of copying). The negation is the whole point of the option here: because `.nuxt` is gitignored it is not copied into the sandbox, and the partial tree that `buildNuxt` regenerates there has no `tsconfig.app.json`, the root `tsconfig.json` references it, and every spec then dies in oxc with `TSCONFIG_ERROR`. Stryker reports that as a bare "No tests were found".
- **No `packageManager` key.** Setting it makes Stryker run `pnpm install` inside the sandbox, where `node_modules` is a symlink back to the real one — pnpm rewrites the real `node_modules/.modules.yaml` to point `virtualStoreDir` at the sandbox, and every later pnpm command in the project demands to purge `node_modules`. Never run pnpm with a working directory inside `.stryker-tmp` either; the recovery is `CI=true pnpm install --frozen-lockfile` from the project root.
- **`ignoreStatic: true`** — `web/mocks/setup.ts` swaps `globalThis.$fetch` at module scope, and a static mutant forces a full environment reload per mutant against that load-order-sensitive capture.
- **`vitest.related: false`** — related-file resolution across Nuxt's vite pipeline can silently fail to find the covering tests, which surfaces as a whole file reported `Survived`. Per-test coverage already selects the right specs.
- **`hookTimeout: 60_000` in `vitest.config.ts`**, not in this config but load-bearing for it: without the raise a cold sandbox skips whole spec files and their mutants all read `NoCoverage` (see below).

One more trap: **`--logLevel debug` crashes the run outright** — the vitest runner `JSON.stringify`s the resolved vite config in `VitestTestRunner.init`, and that config is circular (`projects` closes the loop). It dies with `TypeError: Converting circular structure to JSON` before any test runs, which reads as a Stryker bug rather than a logging one. Use the default level; to inspect what the dry run actually did, `--dryRunOnly --cleanTempDir false` and run vitest against the sandbox by hand.

`concurrency: 4` is a portable default, not a tuned one. Measured on 16 cores: 4 → 1m32, 8 → 1m20, 12 → 1m30. Raising it toward half the core count is worth a measurement on a given machine; Stryker's own default (`cores - 1`) is past the knee, because each worker boots its own Nuxt vite server. `disableTypeChecks` was measured at its default versus `false` — identical score, no time saved — so it stays untouched.

Anything that puts a second copy of this repository inside the working tree — a crashed Stryker sandbox, a `git worktree` under `.claude/worktrees/` — gets collected by vitest as if it belonged here, and every spec runs twice, once against the wrong tree. Both are excluded in `vitest.config.ts`; a sudden doubling of the test-file count is that failure, not a broken change.

Current figures, measured on the merged trees (re-measure before trusting: `pnpm test:mutation`): `master` **92.76%** total / **95.60%** on covered code (539 mutants); `variant/vuetify` **82.98%** / **89.34%** (858 mutants); `variant/nuxtui` **90.17%** / **92.15%** (884 scored mutants: 798 killed, 68 survived, 19 without coverage), measured 2026-08-24. It replaces 76.61% / 88.86%, and three changes moved it for different reasons: the skipped-spec fix below made 88 previously invisible mutants count (total up, covered score _down_, nothing tested), then specs for `AuthControls`, `SidebarNav` and the drawer toggle, then the `UserFormDialog` triage killed 11 of the 15 the first fix exposed. **The branches' totals are not comparable**: the same globs run over very different surfaces — master's `.vue` contribution is 20 mutants across three files, the variant's is several hundred across nineteen. Compare the covered-code score, or compare per file. A corollary proven here twice: a template-only feature moves the number not at all (the table's loading states arrived with four specs and left the score identical to the mutant), so read the score as a statement about scripts, never about the app.

**Resolved 2026-08-24 — a skipped spec file reports as covered by nothing.** The 2026-08-21 run's unexplained `NoCoverage` rise (70 → 122) was `UserFormDialog.vue`'s whole file, 88 mutants of it. `@nuxt/test-utils` runs `setupNuxt()` in a `beforeAll` once per nuxt-environment spec file, and against a **cold** transform cache that hook can exceed vitest's 10s `hookTimeout` default. Vitest then **skips every test in the file while still reporting them**, so Stryker's dry run counts the full 343, announces success, and records the file as covered by nothing. Every mutant in it reads `NoCoverage`.

The failure is silent in both directions: `pnpm test` stays green because the real tree's cache is warm, and the mutation run never says a file was skipped — the score just drops. The tell is a file at exactly 0 covered mutants; the check is a spec whose tests cover nothing **anywhere** (`coveredBy` empty across every file), which is what a skipped file looks like and an untested one does not. `vitest.config.ts` now sets `hookTimeout: 60_000`.

This also explains the targeted-run instability recorded above: a sandbox is cold, so which specs blow the hook budget varies run to run, and identical code measures differently.

Stryker reports several mutants per line, so before writing a test against a survivor, read its `replacement` in `reports/mutation/frontend.json` — a guard's outer condition and its inner operand are separate mutants, and sabotaging the wrong one proves nothing.

Accepted surviving mutants — recheck when touching the code they live in:

- **The `typeof x !== 'object'` operand** in `getValidationErrors` and `gqlFetcher`'s `toValidationBody` — reachable only for a truthy non-object, and every such value already yields `{}` through the string-array message filter below it. The guard is defense-in-depth the filter provides anyway.
- **`RedirectDecision.reason`** (all three strings) — written and never read anywhere in `web/`; diagnostic metadata, not behavior. The day something displays or logs it, its test kills these.
- **`.some` → `.every` on `guestOnlyPrefixes`** — the list holds one prefix, so the two are equivalent; a second prefix makes this killable and should arrive with the test that adds it. (Master only — the variant has no prefix list.)
- **`credentials: 'include'` in `fetcher`** — MSW intercepts below the point where credentials mode is observable, so no test at this layer can see it. The browser enforces it, and the session feature covers the effect.
- **The empty `default:` branch** in `handleApiError` — a Stryker artifact on a `break` with no behavior.
- **`sameAs(password, 'password')`'s second argument** — the field label inside the message, not a contract; same reasoning as the backend's copy mutants.
- **`parseResponse`'s `console.error` text** — `conventions/testing.md` prohibits asserting on logs.
- **`auth-loader`'s `catch` block** — deleting `resetUser()` changes nothing: the store is always empty when the plugin boots, so the reset is defensive against a state the app cannot be in.
- **`useCookieConsent`'s `maxAge` arithmetic** (two mutants) — a cookie's lifetime is not readable back through `document.cookie`; the browser enforces it.
- **`'declined'` → `''`** — both values mean "decided, and not consented" to every reader of the composable, which is the only thing that reads the cookie. Killable the day something else reads the stored string.
- **`app.vue`'s `useHead` block** (7 mutants — the title, the favicon link, the object and array around them) — document metadata is copy, not contract.
- **`app.vue`'s `decision.shouldRedirect && decision.redirectTo`** — the second arm is unreachable through `authRedirectLogic`, which never returns a redirect decision without a target; a type-narrowing guard covered by its own spec.
- **`CookieConsentBanner`'s `isMounted` initial value** — a flash guard for the first client frame; under `ssr: false` there is no hydration pass for it to protect against, so no assertion at this level can see it.
- **`layouts/Default.vue` residue** (variant) — the `useLogOut` options object, the drawer's initial value, and the three `errorHandling` literals, none of which a test can distinguish.
- **`UserCard`'s resend toast message, `defineExpose`, and optional-chaining fallbacks** (variant) for a `user` the store cannot hold as null while the card renders.
- **`handleAfterLeave` in the three auth dialogs** (variant, `NoCoverage`) — each puts its whole reset on the dialog's `after-leave`, which never fires under happy-dom (the Web Animations limit in the not-observable list below); the reset stays on the browser walk.
- **`if (valid)` in the three auth dialogs** (variant) — `handleConfirm` cannot run against an invalid form through any path a user has: the confirm button is bound to `r$.$invalid`, and `FormCard`'s Enter handler returns early on `confirmDisabled`. Defensive, same category as the backend's route-unreachable code.
- **`const form = ref({…})` → `{}`** in `ForgotPasswordDialog` and `RegisterDialog` (variant) — the fields render an absent key and an empty string identically through `v-model`, and Regle's `required` refuses both. On `variant/vuetify` `LoginDialog` is the exception, its initial value being the development credentials the spec asserts; on `variant/nuxtui` it survives there too, because that branch's spec fills the fields itself rather than reading what they came with.
- **Environment-bound template behaviours** (variant) — the not-observable list after the table (overflow borders, viewport `calc()` strings, `after-leave`); `UsersTable`'s five script mutants are all measurement machinery while its actual row policy is template-only and never mutated.

### Browser walk, 2026-09-03 — the scroll and layout rules

The half that cannot be unit-tested, measured in Chromium at 393x760 DPR 2.625 and 760x393 landscape, against the real API. Redo this walk when either rule's implementation changes.

- **Per-edge scroll rules behave.** The users table reported `edge-bottom` at the top of its scroll (top border `rgba(0,0,0,0)`), both edges in the middle, and `edge-top` alone at the end — the state a single region-level boolean gets wrong at both ends. The colour resolved to `rgb(134, 142, 150)`, the `--color-scroll-edge` token. Both border widths read 1px in every state, so only the colour changes and no edge toggle moves content.
- **The dialog bug was real, and it is landscape that shows it.** With the panel unbounded, as it was before this change, the create-user dialog rendered 781px tall in a 393px-high viewport with its submit button 169px below the fold and `document.documentElement` unable to scroll — genuinely unreachable. Bounded, the panel is 361px, the body scrolls, and the button is reachable. In **portrait** English the same panel overflowed by only 10px and the button stayed on screen, so a portrait-only check would have found nothing. Walk this one in landscape.
- **`UIField`'s two-line reservation is the right size, measured rather than chosen.** In `sr-Cyrl` the email format message renders on **two** lines at a 311px box width inside the dialog. The reservation resolved to 36.4px (2 x 18.2), and introducing the error changed no field height and grew the dialog's content by 0. The previous one-line reservation would have grown that field by a line and pushed every field below it, plus the submit button.
- **Reserved labels hold the widest variant.** Each `UIReservedLabel` box measured equal to its widest ghost rather than its shown text — logout holds 115.9px while showing the shorter `Одјава`, and the role column holds 106.4px whether the row reads `Корисник` or `Администратор`, which is what stops an auto-layout table re-widthing on a role change. Accessible names carry the active variant only.
- **Correction to the table-split commit.** That commit's message says the sticky column headers cover the scroll region's top edge rule. They do not: the sticky `th` begins 1px _inside_ the container's border box, so the rule paints above the header band and is visible when scrolled. Kept as it is rather than suppressed — the blue band is present whether or not content is hidden above, so it signals nothing on its own, and the rule does.
- **Not exercised:** the 1px comparison tolerance. Chromium returned integral scroll metrics at DPR 2.625, so the fractional case the tolerance exists for did not arise live; it is covered in `utils/_tests/scrollEdges.spec.ts` instead.

### `variant/nuxtui` — survivors accepted in the 2026-08-21 triage

This branch's own list, kept apart from the shared one above because several entries there describe `variant/vuetify` components (`FormCard`, `UIDialog`, `UsersTable`) that do not exist here.

**Triaged 2026-08-24.** The `hookTimeout` fix made `UserFormDialog.vue` measurable for the first time and exposed 15 survivors. Eleven were killed: the role option set (6, above), `isSaving`'s `||` (3 — it drives the submit button's spinner _and_ its label, so an `&&` leaves the button live and re-submittable through the whole request), `formFor`'s per-key fallbacks (1 — the blank-create test checked only the first field), and `accountEmailRules`' `ignoreId` getter (1 — an edited user's own address read as taken, asserted now through a handler that answers honestly rather than the blanket `available: true` the other tests use). The four that remain are each covered by a standing entry below.

- **`destroyOnClose` in `AuthControls.openAuth`** (2, the object and the boolean) — equivalent, checked by flipping it. `openAuth` calls `overlay.create()` on every open, so a fresh instance mounts whether or not the closed one was destroyed; the reopen-is-fresh behaviour the flag reads as protecting is provided by the create, and its test stays green without it. The flag states the intent and matches the branch's dialog convention (`web/CLAUDE.md`). Every entry below was checked the way this document prescribes — the source was broken by hand and the spec run — rather than reasoned from the report.

- **The always-emit half of `handleOpenChange`** (6, one per dialog) — `if (!next)` → `if (true)`, which forwards `close` on every open-change rather than only on close. A dialog is created already-open through `useOverlay` with `destroyOnClose` and its handle is single-use, so `update:open` never fires with `true` and the two behave identically. The guard states the intent; the dismissal specs kill the other five mutants in each dialog.
- ~~**`hideValidationToast` on `UserGqlFormDialog`** (2)~~ — **killed 2026-08-24; the flag was never inert, the fixture was wrong.** The spec's GraphQL error carried no `extensions.status`, so `toFetchError` fell back to 500 and `handleApiError`'s `statusCode === 422` gate never opened — which looked like the flag doing nothing. The server does stamp it (`RestStatusHandler`, asserted on this mutation in `tests/Feature/GraphQL/UpdateUserMutationTest.php`); with a faithful fixture, flipping the flag off yields three copies of the message instead of one, and that is now asserted.
- **The five success toasts' `'success'` severity** — `toast.spec.ts` owns the type-to-colour mapping, and the only dialog-level observable is a generated colour class, which `stacks/frontend/nuxt/ui/nuxtui/customization.md` forbids reaching into. The message text is asserted instead.
- **`emailRules`' `ignoreId?.()` → `ignoreId()`** — equivalent through Regle, which absorbs a throwing param getter and passes `undefined` to the validator; the request goes out without `ignore_id` either way. Verified: the whole spec passes under the mutant, request and verdict unchanged.
- ~~**The `roleItems` label computeds in both user dialogs**~~ — **killed 2026-08-24; the acceptance was wrong.** It reasoned from the rendered listbox, which jsdom genuinely cannot drive, and concluded the option set was unassertable. But the specs already reach that control at its component seam to _drive_ it (`pickRole`), and the same seam reads its `items` prop. Both dialogs now assert the exact two-role set, which kills all six mutants in each: the computed, the array, both option objects and both label keys. The set is contract, not presentation — an empty or mislabelled list is a role nobody can assign.
- **`UFormField`'s four timing mutants** — checked by hand 2026-08-24, the way this document prescribes: each broken in the source, the spec run, and then a throwaway probe written specifically to catch it. All four survived both, so they are equivalent, not untested. `isLeaving.value = false` in the timeout callback (1): nothing reads the flag while no message is displayed, and the watcher clears it synchronously before a new error renders. `{ immediate: false }` (2, the object and the boolean): VueUse would start the timer at mount, where the callback is a no-op — `isLeaving` is already false and `displayedError` is already `props.error` — and every path that matters calls `start()` or `stop()` first. `.filter(Boolean)` in the `fieldUi` join (1): with no call-site `ui.error` the array contributes an empty string, and the leading space it leaves is tokenised away by `classList` and normalised by tailwind-merge.

Four of `variant/vuetify`'s component behaviours are **not observable at this level** and stay on the live browser walk, each recorded where a reader would look for it — in the spec that would otherwise be expected to cover it:

- **`after-leave`** (`CardDialog`, `UserDetailsDialog`, and the whole reset in each of the three auth dialogs) — `v-dialog` fades through `VDialogTransition`, whose leave hook measures the activator and drives the fade with the Web Animations API. happy-dom has no `Element.prototype.animate` and no layout, so the hook never reaches its `done()` callback: the dialog closes, silently. This is the contract that lets a dialog hold its subject's name in the title without it blanking mid-fade.
- **`FormCard`'s scroll borders** — `isOverflowing` compares `scrollHeight` to `clientHeight`, both `0` without layout, and its only output is a CSS class.
- **Viewport-bounded heights** (`UsersTable`, `LoadingSpinner`) — `useElementBounding` reports every element at top `0`, and the output is a `calc()` string bound into a scoped style.
- **`CardDialog`'s `xs` fullscreen branch** — "fullscreen" exists only as a CSS class.

One divergence on `variant/vuetify` worth keeping in view: `handleEnterKey` exists in three near-identical copies. `FormCard` and `FullScreenDialog` guard on `closest('button, a, textarea, .v-select')`; `UserCard` guards on `'button, a'` alone. Removing `UserCard`'s guard changes nothing observable — the Vuetify button already swallows the key, and the card renders neither a textarea nor a select — so it was left as it is rather than widened to match. The guards in the other two are load-bearing: they cover plain slot content, and removing either turns their specs red.

- The SPA and API must run on the exact origins in `SANCTUM_STATEFUL_DOMAINS` / `FRONTEND_URL` (`localhost:3000`/`3001` + `localhost:8000`) or auth silently fails on cookies/CORS.

## CI

GitHub Actions (`.github/workflows/ci.yml`), on push to `master`/`variant/**` and on PRs. Two jobs: frontend (oxlint, oxfmt check, typecheck, vitest with coverage — Node 24 + pnpm) and backend (pint check + Pest with coverage against a `mysql:8` service container whose `MYSQL_DATABASE` is `vanguard_testing`; job-level `DB_*` env vars override the phpunit/.env values). Coverage is printed, never gated (ADR 013); CI's driver is PCOV via `setup-php`, while local runs use Xdebug. No deploy step — deployment remains an honest gap (ADR 001).
